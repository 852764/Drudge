# 持久化计划与验收记录

`update_plan` 保留原来的 `step` / `status` 格式，新增可选的 `acceptance` 与 `evidence`。非空、未全部完成的计划必须恰好有一项 `in_progress`。

```json
{
  "plan": [
    {
      "step": "补回归测试",
      "status": "completed",
      "acceptance": "新测试及原有测试全部通过",
      "evidence": "python -m unittest discover -s tests -v；退出码 0；对应 run/output ID"
    },
    {"step": "审阅差异", "status": "in_progress"}
  ],
  "explanation": "测试完成，开始审阅"
}
```

存在验收条件的步骤，填写非空证据后才接受 `completed`。**证据是模型/操作者记录的文本，并非系统自动验证的测试结论**；输出 ID、测试日志和代码差异仍需核验。省略验收条件时，旧调用格式保持兼容。

## 生命周期

- 新一轮提示不清空计划；重启后 `/resume` 恢复计划和验收记录。
- `/compact` 后在新系统上下文中重新注入当前计划，不依赖摘要记住进度。
- `/plan` 只读显示计划、持久化状态、修订号、验收条件和证据；控制字符以转义文本显示。
- `update_plan` 传 `plan: []` 显式清空，清空也会持久化；新任务可整体替换旧计划。
- `/new` 开始空计划；关闭 storage 时仅在当前进程中保留。
- `/fork` 在同一事务中复制当前计划快照，后续修改互相独立。父会话的证据属于历史工作，父输出 ID 仍要切回父会话读取；不复制审批或撤销权限。

## 一致性与迁移

新增 `session_plans` 表，不重写历史表。保存同时检查会话消息/上下文水位和计划 revision；过期消费者在模型调用前或计划写入时得到冲突提示，应重新 `/resume`。模型不接受 session、workspace、revision 或 host context 参数。

计划及其 run 审计事件事务提交，数据库写入失败不更新内存计划。最多 32 步、32,000 个序列化字符；每步标题最多 500 字符、验收条件 2,000 字符、证据 4,000 字符。SHA-256 绑定会话、工作区、版本和计划内容，只用于发现损坏，不作为身份认证。不同工作区、校验不符和未知版本会在恢复前报错，原始会话历史保持不变。

自动测试覆盖旧库升级、重复初始化、重启/压缩/分支、隔离、陈旧消费者、写入回滚、参数注入及两种 API 的工具协议。
